# Agent / LLM 应用 / 后端面试市场校准报告

> 调研日期：2026-07-16  
> 用途：校准 `kylin-os-agent` 的学习顺序、项目产物和面试准备方向  
> 样本：牛客 13 篇、小红书 3 篇、抖音 2 篇，共 18 篇网页原帖  
> 技术核验：LangChain、LangGraph、LangSmith、MCP 官方文档

## 0. 结论先行

### 0.1 总判断

当前方向不是“学错了底层”，而是：

**基础原则合理，但路线执行顺序失衡，同时缺少 RAG、Agent 评测回归、上下文/延迟/成本三组高频岗位能力。**

更具体地说：

1. `AGENTS.md` 的主张基本正确：使用主流框架、真实环境、测试、可观测性和安全边界，这些都能在面试证据中找到支持。
2. `AGENT-CHAIN-ROADMAP.md` 是方向偏差的主要来源：12 条链路几乎串行，核心 Agent 到链路 05 才出现，测试到链路 12 才出现，RAG 和独立评测链路缺失。
3. 配置、HTTP、状态、安全、审计不是无用底层。问题是它们被安排成“先全部深挖，再看到 Agent 价值”，而市场更看重候选人能否先跑通并解释一个真实端到端系统，再从真实 Badcase 深化这些能力。
4. app_v2 选择 LangGraph 并不是根因。它适合状态、审批、恢复和长流程；真正的问题是没有先做薄的可运行纵切，也没有同步建立 RAG 和评测证据。
5. app_v3 的旧 `AgentExecutor` 对比已经落后于当前 LangChain 主线。现代 `create_agent` + middleware 应该提前作为薄对比出现，但不应再维护第二套完整产品。

### 0.2 立即纠偏

学习和项目推进改成五轮：

| 轮次 | 先拿到的证据 |
|---|---|
| V0 | 依赖、配置、导入、启动、health、启动测试 |
| V1 | app_v2 可演示 Agent、一个真实工具、thread、Trace、自动化测试，以及现代 `create_agent` 薄对比 |
| V2 | RAG、版本化评测集、检索/回答指标、Badcase 回归 |
| V3 | 权限、HITL、注入防护、幂等、循环/费用熔断 |
| V4 | SSE、取消/背压、并发限流、缓存、负载测试和部署 |

这不是降低工程标准，而是把工程标准放到真实功能和真实失败旁边学习。

## 1. 调研方法

### 1.1 研究问题

本次调研只回答四件事：

1. Agent 开发、LLM 应用开发和相邻后端岗位，面试官实际追问什么？
2. 哪些问题反复出现，哪些只是偶发八股？
3. 当前沙盒已经覆盖什么，缺什么，哪里学得过早或过深？
4. 应如何修改长期协作规则和项目路线，而不是只生成一份题库？

### 1.2 纳入标准

样本必须同时满足大部分条件：

- 网页原帖可打开，能回溯到具体作者、时间或原帖 ID。
- 明确属于 Agent、LLM 应用、RAG、AI 后端或强相关后端岗位。
- 至少包含面试轮次、项目追问、具体问题、场景题、结果或可验证互动数据中的两项。
- 优先近期、高互动、大厂/主流团队、问题具体且具有工程语境的内容。
- 不把单纯“学习路线”“题库广告”“可下载资料”“培训引流”作为有效面经。
- 相同正文的跨平台搬运只计一次；标题与正文公司不一致的样本剔除。

高点赞只用于发现候选，不代表技术正确。技术结论再用当前官方文档核验。

### 1.3 证据等级

| 等级 | 标准 |
|---|---|
| A | 一手语气、轮次和问题具体，含结果/团队/项目上下文之一，互动或评论能辅助验证 |
| B | 问题具体且可回溯，但结果、身份或上下文不完整 |
| C | 主要是二次整理、题库或营销内容；不进入主样本 |

本报告的频次来自人工主题编码，表示方向性，不是岗位总体概率。

## 4. 三类岗位真正需要的能力

### 4.1 Agent 开发工程师

必须会：

- 把任务拆成状态、路由、模型、工具、停止条件和恢复点。
- 比较 ReAct、Plan-and-Execute、Workflow、单 Agent、多 Agent 的适用边界。
- 设计 Tool Schema、工具发现、参数校验、超时、重试、幂等、权限和失败回传。
- 理解 MCP 的 tools/list、tools/call、输入/输出 schema 和错误语义；能区分协议、工具和 Agent 编排层。
- 管理 thread 状态、短期上下文、长期记忆，以及何时澄清或进入 HITL。
- 为长任务设置步骤、token、时间、工具调用和费用预算，支持 checkpoint/resume/kill switch。
- 用 Trace 和评测集定位路由、模型、工具、检索或最终回答的 Badcase。

### 4.2 LLM 应用开发工程师

必须会：

- RAG 全链：解析、chunk、Embedding、稀疏/稠密召回、混合排序、rerank、引用和生成。
- 用数据选择 chunk、top-k、权重和模型，而不是只讲“经验值”。
- 处理查询改写、信息不足、多轮澄清、表格/图片和结构化输出。
- 区分 RAG、长上下文、微调/SFT 的收益、成本、数据要求和风险。
- 建立离线数据集和在线采样，分别评估检索质量、回答质量、延迟和成本。
- 解释 Prompt 版本、模型版本、结构化输出、缓存和回归策略。

### 4.3 Agent/LLM 相邻后端工程师

必须会：

- Python/Go/Java 至少一门主语言的并发、异常、资源管理和测试。
- HTTP、SSE/流式响应、超时、取消、背压、限流和稳定错误契约。
- MySQL 索引、事务、MVCC、锁和慢查询；Redis 数据结构、缓存一致性与分布式限流。
- 进程/线程/协程、GIL/锁等与实际服务吞吐和排障的联系。
- 日志、指标、Trace、配置、依赖、部署和线上故障定位。

### 4.4 三类岗位共同的“项目表达”

一个项目至少能讲清：

1. 用户问题和为什么值得用 LLM/Agent。
2. 输入输出、约束、数据、外部系统和失败模式。
3. 架构图与一条真实 Run 的调用顺序。
4. 为什么选当前框架，放弃了什么方案。
5. 数据集、指标、基线、改动前后结果。
6. 最难的 Badcase、如何定位、如何避免回归。
7. 延迟、成本、吞吐、安全和可维护性取舍。
8. 自己真正负责的边界，而不是团队共同成果。

## 5. 面试官高频追问地图

### 5.1 项目与架构

- 你的系统为什么需要 Agent，而不是固定 Workflow 或普通函数调用？
- 选择 LangGraph、`create_agent` 或自研的理由是什么？迁移成本是什么？
- 单 Agent 还是多 Agent？子 Agent 的职责、共享状态和失败隔离如何设计？
- 首轮请求和多轮补充如何路由？信息不足时怎样让用户补充？
- 展开一次真实 Run：每一步的输入、输出、超时、错误和停止条件是什么？
- 线上效果和业务价值如何证明？你负责了哪一段？

### 5.2 RAG

- 为什么同时使用 BM25 与 dense retrieval？如何融合？
- chunk 大小、重叠、父子索引、top-k 和 rerank 截断如何确定？
- 如何分别评估召回相关性和最终回答？数据集从哪里来？
- 查询改写什么时候会伤害召回？怎样保留原查询和做多路检索？
- 表格、图片、代码或超长文档怎么切分和索引？
- RAG 的延迟和成本如何优化，哪些优化会损害质量？

### 5.3 上下文与记忆

- state、短期记忆、长期记忆分别存什么？作用域是什么？
- 什么时候摘要，什么时候检索，什么时候直接保留原文？如何验证信息没有丢？
- 如何处理记忆污染、过期、冲突、用户纠正和隐私删除？
- 长短记忆如何协同，怎样避免把全部历史都塞进 prompt？
- Skill/工具很多时如何渐进披露，避免 context 过大和错误触发？

### 5.4 Tool、MCP 与可靠性

- Tool Schema 怎么设计，如何让模型选对工具和参数？
- MCP 与 Function Calling、Tool、Agent 的层次和边界是什么？
- 工具超时、部分成功、重复调用和不可用时怎样恢复？
- 有副作用的工具怎样做幂等、审批、审计和补偿？
- 工具返回网页/日志中的恶意指令时怎样隔离？

### 5.5 评测与优化

- Agent 的任务成功如何定义？没有唯一标准答案怎么办？
- 离线评测集如何构建、分层、版本化和避免污染？
- Prompt 调优“修好一类、坏了另一类”如何发现和处理？
- 一个 Badcase 如何归因到路由、检索、上下文、工具、模型或输出？
- 什么时候换模型、调参数、改 Prompt、改检索、上 SFT？
- 没有用户反馈时怎样做在线抽样、自动评审和人工复核？

### 5.6 后端与性能

- SSE 流式接口如何处理客户端取消、超时和背压？
- QPS 高峰时模型、检索、工具和数据库各自的瓶颈怎么定位？
- 令牌桶、漏桶、滑动窗口如何选，Redis 中如何实现？
- 缓存什么，key 如何设计，如何处理陈旧、击穿和一致性？
- TTFT、总延迟、吞吐、token/费用怎样采集和优化？
- MySQL 索引、事务、MVCC、锁和慢查询怎样影响真实 Agent 服务？

## 6. 大厂常见场景题与回答骨架

回答场景题不要直接报框架名。建议顺序：**目标/指标 → 约束 → 链路 → 失败模式 → 观测与评测 → 取舍**。

### 场景 1：Agent 经常选错工具

应覆盖：

- 从 Trace 统计“未调用、误调用、参数错、结果错、重复调用”五类错误。
- 检查工具边界、命名、description、schema、示例和重叠能力。
- 用路由/候选集缩小可见工具，危险工具先策略校验，不只依赖 prompt。
- 建立版本化回归集；比较改 schema、改路由、换模型后的成功率、延迟和成本。
- 对副作用操作加入幂等键、HITL、审计和补偿路径。

### 场景 2：长任务陷入循环或费用失控

应覆盖：

- 明确任务完成条件和可验证中间产物。
- 设置模型调用、工具调用、步骤、token、时间和费用预算。
- 检测重复状态、重复工具参数和无进展循环。
- checkpoint 后可暂停/恢复；超预算时返回部分结果和继续建议。
- 提供取消、kill switch、Trace 和告警，不把“最大轮数”当唯一方案。

### 场景 3：Prompt 调优出现回归

应覆盖：

- 冻结分层数据集和指标，按场景/难度/风险看切片结果。
- Prompt、模型、检索配置、工具版本全部可追踪。
- 对比改动前后的任务成功、格式正确、工具正确、延迟和成本。
- 分析是否应改上下文/检索/工具，而不是继续堆 Prompt。
- 自动评审只作信号，对高风险或分歧样本人工复核。

### 场景 4：RAG 相关性和回答都不好

应覆盖：

- 先分离解析、切分、召回、重排和生成，避免只看最终答案。
- 建立查询-相关文档标注；测 Recall@k、MRR/nDCG 等检索指标和回答指标。
- 检查 chunk、metadata、BM25+dense、权重、query rewrite、rerank 与 top-k。
- 用失败切片决定优化，不盲目换向量库或扩大上下文。
- 记录延迟/成本，给出质量与性能取舍。

### 场景 5：一千条数据需要求和，Agent 怎么设计

应覆盖：

- 数值计算交给确定性代码/数据库/工具，不让 LLM 逐条“推理”。
- 输入校验、分批、并行度、失败重试、幂等和最终校验。
- LLM 负责理解意图、选择数据源、生成计划和解释结果。
- 对大规模扩展说明流处理、MapReduce/SQL 聚合、资源与审计。

### 场景 6：工具输出包含 Prompt Injection

应覆盖：

- 把网页、日志、文件和工具输出视为不可信数据，不提升为系统指令。
- 限制工具权限和数据流；模型输出不能直接成为高风险工具参数。
- 内容扫描只是信号，还需要策略校验、参数约束、HITL 和审计。
- 用对抗样本测试是否能诱导泄密、越权、额外工具调用或规则覆盖。

### 场景 7：线上高峰流式接口卡顿

应覆盖：

- 分解 DNS/连接、检索、排队、模型 TTFT、生成、工具和序列化耗时。
- 采集 p50/p95/p99、并发、队列、token 速率、取消率和上游错误。
- 设置连接池、超时、并发隔离、限流、背压和客户端取消传播。
- 缓存可复用检索或稳定前缀，同时说明陈旧和命中率风险。
- 用负载测试验证，不只给理论优化清单。

## 8. 哪些“底层”该学，哪些学得过早

### 8.1 面试中真实有价值的底层能力

- 进程、线程、协程、GIL、锁和并发控制。
- HTTP/SSE、超时、取消、背压、连接池和错误契约。
- MySQL 索引、事务、MVCC、锁；Redis 缓存和分布式限流。
- 向量检索、ANN、BM25、rerank 的原理与工程取舍。
- Tool Calling schema、幂等、重试、权限和审计。
- TTFT、吞吐、KV Cache、batching、成本和故障定位。

这些不是本末倒置，因为它们直接回答“为什么系统在线上可靠”。

### 8.2 当前学得过早或范围过大的内容

- 在第一次 Agent Run 之前，完成全部生产级配置、生命周期和 readiness 设计。
- 在没有真实工具失败和攻击样本前，深挖完整安全策略实现。
- 在没有评测数据前，讨论大量 Prompt/路由优化。
- 同时维护 app_v2 与 app_v3 两套完整产品。
- 自己重做框架已有的状态、结构化输出或 Agent 执行能力，只为了理解底层。
- 把测试、Trace、指标和项目 Demo 留到最后一条链路。

判断标准不是“底层/上层”，而是：它是否服务于当前纵切的真实失败、指标、架构决策或面试表达。

## 9. 偏差成因

### 9.1 主要成因：路线图的严格串行结构

- 链路 01 至 04 全部位于 Agent 路由之前。
- 核心 Agent 行为到链路 05 才出现，工具到 08，测试到 12。
- 横切能力被当成一次性终点，而不是每个纵切逐步加深。
- RAG 和 Agent 评测没有独立所有者。

### 9.2 次要成因：版本信息没有及时回写

- app_v3 仍使用旧 AgentExecutor 路线，而当前 LangChain v1 主线是 `create_agent` + middleware。
- app_v2 的人工审批写法与当前 LangGraph `interrupt()` / `Command(resume=...)` 主线不一致。
- 依赖文件允许无上限 `>=`，旧代码和新包可能组合成不可导入环境。

### 9.3 放大因素：学习协议范围定义过宽

四阶段协议本身没有问题；问题是“链路”被定义得太大。一个基础链如果要完成全部生产级细节才能过四阶段，就会长期阻塞可演示行为。纠偏方式是缩小每轮链路边界，而不是取消认知、运行、测试和迁移闸门。

### P0：现在就做

## 12. 官方技术核验

以下只用于确认技术表述和当前 API，不用官方文档替代市场样本：

1. [LangChain Agents](https://docs.langchain.com/oss/python/langchain/agents)：当前主线为 `create_agent`，支持 middleware、结构化输出、checkpointer/thread、重试、Guardrail 和 HITL 等扩展。
2. [LangChain v1 migration](https://docs.langchain.com/oss/python/migrate/langchain-v1)：确认 v1 的 Agent API 和旧接口迁移边界。
3. [LangChain Context Engineering](https://docs.langchain.com/oss/python/langchain/context-engineering)：把 state、store、runtime context 区分为不同上下文来源，支持本报告对上下文工程的分层。
4. [LangGraph Interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts)：当前人工暂停/恢复使用 `interrupt()`、checkpointer、thread_id 和 `Command(resume=...)`。
5. [LangGraph Persistence](https://docs.langchain.com/oss/python/langgraph/persistence)：区分 thread 内 checkpoint 与跨 thread store。
6. [LangSmith Evaluation](https://docs.langchain.com/langsmith/evaluation)：区分离线数据集/评测与生产 Trace 上的在线评测。
7. [MCP 2025-06-18 Schema](https://modelcontextprotocol.io/specification/2025-06-18/schema)：核验 tools/list、tools/call、输入输出 schema 和 `isError` 语义。

- 框架 API 会变化；易变实现必须在真正修改代码时再次查看官方文档。
